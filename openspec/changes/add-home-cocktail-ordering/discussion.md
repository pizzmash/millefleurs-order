- 同じkind_idの例: ドライ・ジン／タンカレー／スロージン、ホワイト・ラム／ダーク・ラム。
- 指定どおり同一kind_idで代用可能とするが、味や度数の変化を伴い得る。表示度数は原レシピの参考値として扱う案。
- kind_idが空欄の材料にはクラッシュドアイスや好みのリキュールなどがある。空欄同士を同種扱いしない。
- 分量はmlに加え、tsp.、dash、個、スノースタイルなどがある。
- 甘さ・酸味などの構造化された味タグはない。初期版の絞り込みは合意済みのお酒の種類・度数とし、味や技法による絞り込みは含めない。
- 画像は外部URL。利用方法は画面設計時に決める。

## 合意済み（2026-09-06）

- 初期版のアクセス範囲は自宅Wi-Fi内。
- 在庫は「ある／ない」。残量管理と注文による自動減算は不要。
- お酒・ジュース・シロップ・果物を在庫登録対象とする。
- 水・氷は常備品として材料条件を満たす。

- 客人は家主が表示するQRコードからアクセスし、ニックネームを入力して参加する。アカウント登録は不要。
- 客人はカクテルを1杯ずつ注文し、自分の注文状況を確認できる。
- 注文状態は「受付 → 提供完了」の2状態とし、家主が提供完了に切り替える。
- 客人側の注文キャンセル機能は設けない。
- 家主は到着順の注文一覧から、材料・分量・代用品を確認できる。
- 初期版の家主画面には管理用パスワードやログインを設けない。

- カクテル名・材料名で検索し、お酒の種類と度数で絞り込める。
- 「今日は作らない」など、家主が個別のカクテルを非表示にする機能は設けない。
- レシピ指定のdrink_idの在庫を優先する。なければ同じkind_idの在庫を代用候補とし、家主が作る際に選択する。

- サーバーは現在のWindows PC内のWSL2環境で稼働させる。
- 家主・客人ともにスマートフォンからアクセスすることを前提とする。
- 画面は暗めで落ち着いたバー風のデザインにする。

- 注文履歴は継続して保存し、家主画面では受付中を優先表示、提供完了を履歴にまとめる。会の開始・終了操作は設けない。
- 家主の注文一覧と客人の注文状況は画面を開いている間に自動更新する。
- 通知は画面内のお知らせのみとし、通知音・プッシュ通知は設けない。

## 常備品のデータ対応案

- 水: drink_id=90。熱湯（drink_id=70）は水と同じkind_id=60であり、同種代用ルールにより満たせる。
- 氷: クラッシュドアイス（drink_id=67、kind_id空欄）を明示的に常備品に含める。
- 名前の部分一致で常備品を決めない。アイスコーヒーやバニラアイスクリームは常備の氷に含めない。

## 画面構成案（未合意）

- 配色: チャコールの背景、アイボリーの文字、控えめなアンバーのアクセント。
- 客人: カクテル一覧（検索・絞り込み）、詳細・注文、自分の注文。
- 家主: 受付中の注文、提供完了の履歴、在庫管理、参加用QRコード。
- スマートフォンで押しやすいボタンと読みやすい文字を優先する。

## 実装時の接続確認

- WSL2のネットワーク構成を確認してからLAN向けの起動手順を決める。

- QRコードにはスマートフォンから到達できる参加用URLを使う。
