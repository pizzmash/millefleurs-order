## Context
Cloudflare Workers + D1。注文は1件1杯でrequest_keyにより重複を防止する。不変カタログだけをキャッシュしている。

## Goals / Non-Goals
バー別の人気を表示し、家主が集計をゼロから再開できるようにする。個別リセットや期間別分析は対象外。

## Decisions
- カウントは提供完了時ではなく新規注文の受付成立時に1加算。失敗・再送・提供完了では加算しない。
- (bar_id, cocktail_id)を主キーに累計と最後の受付時名称を保存。AFTER INSERTトリガーで注文保存と原子的に加算し、並行送信でも取りこぼさない。既存注文は移行時に全状態を集計する。
- カタログの更新や在庫変動から独立させる。客人は作成可能な対象だけを検索・絞り込み後、注文数降順→日本語名昇順→ID昇順でソートしてから24件ずつページ化する。未注文は0。次回画面取得時に反映し、定期ポーリングは増やさない。
- 家主は「注文」の受付中・提供完了履歴と並ぶ「注文数」タブで確認する。下部ナビを増やさず注文関連の操作を集約する。全現行カクテル（在庫なし・0杯も含む）とカタログから消えた集計を名前で検索し30件ずつ表示。合計は検索に関係なくバー全体を示す。表示中30秒ごとに更新する。
- リセットは確認文とキャンセルを挟み、所有バーの全カウントを単一UPDATEで0にする。実行中は二重操作を防ぎ、失敗は画面内表示。履歴・未提供注文・在庫には影響しない。注文と同時の場合はDBの実行順で、リセットより後の新規注文だけを残す。リセット前の注文の再送は加算しない。
- APIは既存家主認証・Origin検証を使用し、バーIDは認証情報から決める。集計はキャッシュせず毎回所有バーだけ取得する。

## Risks / Trade-offs
D1移行をWorker更新前に適用する。トリガーは旧Workerの注文や旧LAN履歴の取り込みも集計できる。カタログから消えたカクテルも家主の累計から隠さない。リセット通信結果が不明な場合、自動再試行せず再取得して確認する。
