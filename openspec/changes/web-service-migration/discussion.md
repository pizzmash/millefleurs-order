# 判断事項

状態: 仕様提案。推奨値で実装計画を具体化しているが、ユーザーが個別に合意した値ではない。

| 論点 | 推奨案 | 別案・影響 |
| --- | --- | --- |
| 家主とバー | 初回は1家主1バー | 複数バー・共同管理なら権限モデルを拡張 |
| DB | D1追加 | R2だけではDBを代替しない。Firestoreならデータ設計を変更 |
| 配信構成 | Pages + API Worker | Workers Static Assetsで一本化も可能 |
| 公開URL | 固定ドメインをPUBLIC_APP_URLに指定 | pages.devでも開始可能。後の変更は紙QRの再配布等が必要 |
| 客人の参加 | QRとニックネーム、登録不要 | 客人認証の追加は別改修 |
| 招待期限 | 再発行まで有効 | 会ごとの期限管理は別改修 |
| 客人セッション | 30日 | 旧招待の再発行時は期限内でも失効 |
| 注文受付 | 新規バーはOFF、家主がON/OFF | イベント作成は不要 |
| ローカルデータ移行 | 在庫・注文履歴を指定した1家主へ移す | マスターのみの新規開始なら移行工程を省略 |
| 買い足し探索 | ブラウザーWeb Worker | サーバー計算ならCPU枠・分散排他・予算を検討 |
| 画像 | 外部URLとPages静的ファイル | R2は不要と判断しユーザー指示で除外済み |
| 公開規模・予算 | 小規模から開始し負荷測定 | 同時利用者・月額上限に合わせて更新間隔等を調整 |
| 保存・削除 | 公開前に運用ルールを決定 | 注文・退会データ・バックアップの保持期間と削除窓口を明示 |

公開作業に必要な実値は本番/stagingのドメイン、Cloudflareアカウント、Firebaseプロジェクト、必要なら既存在庫の移行先UID。仮のアカウントIDやリソースIDは設定ファイルへ書かない。

退会の自動UIは初回の必須機能にしていない。公開前に、ユーザー停止→招待/セッション失効→D1の当該バーデータ削除→Firebaseユーザー削除という再実行可能な運用手順と、バックアップに残る期間を案内する。具体的な保存期間は公開条件として確定する。
