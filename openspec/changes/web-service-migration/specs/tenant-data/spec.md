## ADDED Requirements

### Requirement: バー単位のデータ分離
システムは在庫・客人・セッション・招待・注文をbar_idで分離し、カタログのみ共有すること（SHALL）。所属整合性をDB制約でも保つこと（SHALL）。

#### Scenario: 同じ材料を異なる家主が登録する
- **WHEN** Aが材料を「ある」、Bが同じ材料を「ない」にする
- **THEN** 在庫・作成可能数・代用品・買い足し入力が各バーで独立する。

#### Scenario: 客人を別バーに紐づける
- **WHEN** バーAの客人をバーBの注文またはセッションへ関連付けようとする
- **THEN** DB制約で拒否する。

### Requirement: 明示的な既存データ移行
システムはSQLite移行時にUIDとバーを明示し、バックアップ・dry-run・再実行時の重複防止を提供すること（SHALL）。

#### Scenario: 同じ移行を再実行する
- **WHEN** 同じ元DBと移行IDで再実行する
- **THEN** 注文を重複させず、別バーへコピーせず、結果件数を確認できる。

#### Scenario: 旧客人の履歴を移す
- **WHEN** 過去の注文を移行する
- **THEN** スナップショット・時刻・状態を保持し、旧Cookieは新サービスの認証に使えない。

### Requirement: カタログの安全な更新
システムはカタログを明示的に配備し、途中状態を公開せず、在庫と注文履歴を保持すること（SHALL）。

#### Scenario: 取り込みに失敗する
- **WHEN** 新カタログの一部が不正である
- **THEN** 公開中のカタログとユーザーデータを利用可能な状態に保つ。
